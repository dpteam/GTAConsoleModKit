# Динамическая отказоустойчивость

«Динамическая» — значит поведение меняется в зависимости от того, что происходит:
одна упавшая операция не валит процесс, повторяющийся отказ перестаёт долбить
подсистему, а умерший листенер поднимается сам.

## Инструменты (`Core/Resilience.cs`)

| Инструмент | Когда применять | Что делает |
|---|---|---|
| `Guard(name, action)` | любая рискованная операция | ловит исключение, пишет `FAULT`, возвращает `Result` |
| `Guard<T>(name, func, fallback)` | чтение необязательных данных | возвращает fallback вместо исключения |
| `Retry(name, attempts, baseMs, action)` | транзиентный ввод-вывод | экспоненциальный backoff + джиттер, лог каждой попытки |
| `CircuitBreaker` | подсистема, которая «лежит» | после N ошибок открывается, через cooldown пробует снова |
| `Supervisor` | долгоживущий воркер | перезапуск с задержкой 0.5→30 с, сброс задержки после минуты работы |

## Как это применено

- **Задания.** Каждое задание выполняется в `Pipeline` внутри `try/catch`. Исключение →
  состояние `failed`, сообщение и стек — в лог, воркер живёт дальше. Следующее задание
  стартует нормально (проверено: падение `chk-export` на битом файле не мешает следующей
  операции).
- **Пакетные операции.** `ChkFile.ExportAllPng` и `ImgArchive.ExtractAll` обрабатывают
  каждый элемент через `Guard`: один битый файл не отменяет весь экспорт, в лог уходит
  строка с именем именно этого файла.
- **Веб-листенер.** `Supervisor("web")` следит за потоком `AcceptLoop`; если тот умер
  (порт отобрали, шторм сбросов), `WebServer.Restart()` пересоздаёт сокет на том же
  адресе. Задержка удваивается до 30 с.
- **Порты.** `server.webPort` + `webPortFallbacks`: если порт занят, сервер берёт следующий
  и пишет об этом `WRN`.
- **Соединения.** `server.maxConnections` (по умолчанию 64) — лишние соединения
  закрываются сразу, а не копятся. Таймауты 30/60 с на приём/передачу.
- **Файлы.** Всё, что пишется на диск, идёт через `Util.WriteAllBytesAtomic`
  (временный `.part` + `File.Move`), поэтому недописанный образ не выглядит готовым.
- **Конфиг.** Битый `config.ini` не мешает старту: парсер игнорирует непонятные строки,
  а ошибка чтения уходит в лог и берутся значения по умолчанию.

## Осознанно не сделано

- **Нет автоматического восстановления после порчи данных.** Если файл на диске битый,
  тулкит скажет об этом с указанием, что именно не сошлось, но «догадываться» и
  переписывать данные не станет.
- **Нет повторов для операций записи в образ.** Повторная частичная запись ISO/IMG может
  испортить результат сильнее, чем честная ошибка, поэтому такие операции либо
  завершаются целиком, либо не оставляют файла.
- **Circuit breaker не отключает UI.** Он только прекращает долбить подсистему и
  возвращает быстрый отказ с текстом причины.

## Настройки

```ini
[resilience]
retries=3                 ; попытки для Retry
retryBaseMs=200           ; базовая задержка (далее ×2 + джиттер)
breakerThreshold=5        ; ошибок до открытия
breakerCooldownSec=30     ; сколько «молчать»
restartDelayMinMs=500
restartDelayMaxMs=30000

[limits]
maxUploadMb=512
maxJobHistory=200
maxOpsPerSession=5000

[server]
maxConnections=64
```
