# Архитектура

## Слои

```
            ┌──────────────┐   ┌────────────────┐
            │  Web UI      │   │  CLI (headless)│
            │ public/ ES5  │   │ Cli/CommandLine│
            └──────┬───────┘   └───────┬────────┘
                   │ HTTP/JSON         │ прямой вызов
            ┌──────▼───────────────────▼────────┐
            │  Operations (единая точка)         │
            │  Cso, Iso9660, Img, Dtz, Chk, ...  │
            └──────┬─────────────────────────────┘
                   │
   ┌───────────────┴────────────────────────────────────┐
   │ Core: Log · Config · Json · Util · Resilience       │
   │ Workspace/Project/SessionHub · Pipeline             │
   └─────────────────────────────────────────────────────┘
```

Ключевое решение: **вся логика операций живёт в `Operations`**, а CLI и HTTP — только
тонкие адаптеры. Так поведение не расходится между мордой и консолью, и любой баг
воспроизводится одинаково.

## Потоки

| Поток | Что делает |
|---|---|
| main | bootstrap, консольные команды, REPL в режиме `serve` |
| `http-accept` | `AcceptSocket`, лимит соединений |
| `http-conn` × N | чтение запроса, маршрут, ответ, keep-alive |
| `sup-web` | супервизор листенера (перезапуск с backoff) |
| `job-0..N` | фоновые задания (`Pipeline`) |

Соединение обслуживается отдельным потоком (простая и предсказуемая модель для .NET 4.0;
пул потоков тут дал бы больше сюрпризов на XP, чем пользы). Лимит задаётся
`server.maxConnections`, лишние соединения сразу закрываются.

## Проект как единица работы

```
workspace/
  lcs_patch/
    project.json      манифест + журнал операций (seq, время, кто, что)
    files/            рабочее дерево (сюда грузятся файлы игры)
    export/           результаты операций
```

`project.json` — единственный источник правды. Он пишется атомарно (`.part` + rename),
поэтому падение в момент сохранения не оставляет полуфайл.

Файлы операции:
| Поле | Смысл |
|---|---|
| `id` | слаг имени, уникален в workspace |
| `sessionCode` | `ABCD-2345`, генерируется при создании |
| `nextSeq` | следующий номер операции |
| `ops[]` | журнал: `{seq, when, user, kind, target, note}` |
| `files/` | рабочее дерево |

Журнал — он же история совместной сессии. Он ограничен 5000 записями (мягкий кап в
`Project.AddOp`), потому что это лента событий, а не аудит-архив.

## Очередь заданий

`Pipeline` — N воркеров, у задания есть состояние (`queued/running/done/failed/cancelled`),
прогресс 0…100, текстовое сообщение, лог (200 строк) и `result` (JSON). Долгие операции
(распаковка ISO, упаковка IMG, экспорт текстур) не блокируют HTTP: API отвечает `202` с
id задания, клиент опрашивает `/api/jobs/{id}`.

Кооперативная отмена: операция проверяет `job.CancelRequested` в колбэке прогресса и
бросает `OperationCanceledException`, которое воркер превращает в состояние `cancelled`.

## Отказоустойчивость

См. `docs/RESILIENCE.md`. Коротко: `Guard` не даёт исключению уронить процесс,
`Retry` лечит транзиентные ошибки FS, `CircuitBreaker` перестаёт долбить упавшую
подсистему, `Supervisor` поднимает листенер, `Pipeline` изолирует задания друг от друга.

## Безопасность границ

`Util.SafeCombine` не выпускает путь за пределы корня (проверка по полному пути, включая
`..`). API дополнительно разрешает абсолютные пути только внутри `workspace` и `gamesRoot`.
Тела запросов ограничены `limits.maxUploadMb` (по умолчанию 512), заголовки — 32 КБ.

Аутентификации нет: сервер по умолчанию слушает `127.0.0.1`. Для сети — `bind=0.0.0.0`
и reverse proxy с собственной авторизацией.

## Почему свой HTTP-сервер

`HttpListener` на Windows требует URL ACL (права администратора) для нелокальных префиксов
и по-разному ведёт себя на XP. Сокет-сервер не требует ничего и одинаково работает
на XP SP3 и на Windows 11. Плата — свой парсер запросов, зато предсказуемый и без
сюрпризов с `netsh`.
