# Lua-скрипты LCS/VCS (`*.LUA.LC`)

## Почему не unluac

`https://github.com/Jeong-Min-Cho/unluac` — это Java-порт Lua-декомпилятора, и он
рассчитан на **стоковый** формат `luac` (Lua 5.1 / 5.3). Наши файлы — не он:

```
$ hexdump -C CUTSCENEPLAYER.LUA.LC | head -2
00000000  1b 4c 75 61 50 01 04 04 04 06 08 09 09 04 3b af  |.LuaP.........;.|
00000010  ef 4b 08 00 00 00 3d 28 6e 6f 6e 65 29 00        |.K....=(none).|
```

| | стоковый `luac` | наш файл |
|---|---|---|
| подпись | `\x1bLua` | `\x1bLua` + версия `0x50`, но дальше «LuaP»-сборка Rockstar |
| заголовок | 12 байт (5.0) / 18 байт (5.1) | **18 байт со своим набором полей** |
| числа | `double` (8 байт) | **`float` (4 байта)** — доказано константами (`03 00 00 c8 42` = 100.0) |
| константы | теги 5.1: 0/1/3/4 | теги 5.0: 0/1/3/4, строки с длиной **включая NUL** |

Поэтому «встроить unluac» означало бы тащить JRE (а набор принципиально на .NET 4.0 без
внешних зависимостей) и всё равно переписывать его загрузчик под этот формат. Порт
декомпилятора на C# — это ~10 тыс. строк, отдельная большая работа, и делать его до
того, как разобран сам контейнер, бессмысленно.

**Решение: свой разбор, по шагам.** Сначала то, что можно доказать побайтово, потом
дизассемблер, потом декомпилятор.

## Что уже известно точно

```
0x00  1b 4c 75 61 50              "\x1bLuaP"
0x05  01 04 04 04 06 08 09 09 04   размеры/флаги сборки (не совпадают со стоковыми)
0x0E  3b af ef 4b                  тестовое число, 4 байта (float, не double)
0x12  u32 len + bytes              имя источника: "=(none)" у собранных без имени

дальше  заголовок прототипа, ЗАТЕМ непрерывный блок констант, ЗАТЕМ код
```

Запись константы: `tag(1) + payload`

| tag | тип | payload |
|---|---|---|
| `0x00` | nil | — |
| `0x01` | boolean | 1 байт |
| `0x03` | number | **4 байта float** |
| `0x04` | string | u32 длина **включая** NUL + байты |

Код — 4-байтные слова, opcode в **младших 6 битах** (порядок Lua 5.0). Проверка на
`CUTSCENEPLAYER.LUA.LC`: код начинается на `0x169`, длина 62 инструкции, последняя —
`1b 80 00 00` = `0x0000801b` → opcode 27 = **RETURN**. Первая — `05 00 00 01` → opcode 5 =
**GETGLOBAL**. Это ровно то, с чего начинается и чем заканчивается main-чанк.

## Что умеет набор сегодня

```bat
ModKit.exe lua-strings SCRIPTS\MAINLOOP.LUA.LC            :: константы-строки
ModKit.exe lua-strings SCRIPTS\MAINLOOP.LUA.LC --numbers  :: плюс числа (best effort)
```

Извлекаются **константы**: строки — точно (проверяется длина, NUL-терминатор и
печатаемость каждого символа, поэтому мусора из кода в вывод не попадает), числа —
best effort (обычные float в разумном диапазоне; мусорные денормали отбрасываются).

Замер на 18 файлах LCS:

```
файлов: 18, суммарно 263 КБ
строк:  4 246
чисел:  6 439 (best effort)
```

Пример (`STDLIB.LUA.LC`): `string`, `ordinalSuffix`, `list`, `concat`, `filter`, `find`,
`set`, `insert`, `table`, `permute`, `clone`, `deepcopy`. Пример (`GTA.LUA.LC`):
`require`, `stdlib`, `Script`, `Object`, `Start`, `IsRunning`, `Stop`, `StateMachine`,
`_init`, `state`.

Этого уже хватает, чтобы искать в скриптах глобалы движка, печатаемый текст, тайминги и
координаты — без декомпилятора.

## Что дальше

1. Разобрать заголовок прототипа (порядок полей и их размеры) — тогда появятся границы
   констант и кода, и числа станут точными, а не best effort.
2. Дизассемблер `lua-disasm`: таблица opcode'ов Lua 5.0 (38 штук) + вывод в стиле `luac -l`.
3. Декомпилятор: CFG + восстановление выражений. Это уже сопоставимо по объёму с
   unluac, но на своём рантайме и поверх проверенного загрузчика.

## Тесты

`lua-strings reads the constants of a LuaP chunk` — синтетический чанк с заголовком,
строкой, числом и строкой: проверяются обе строки, число и счётчик.
`lua-strings refuses a file that is not a Lua chunk` — на нулевом файле честная ошибка.
